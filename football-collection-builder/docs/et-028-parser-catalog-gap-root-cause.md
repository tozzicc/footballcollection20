# ET-028 — Parser/Catalog gap root-cause diagnosis

## 1. Resumo executivo

Auditoria read-only de ponta a ponta das 335 colecoes preservadas pela ET-027 como `PARSER_OR_CATALOG_GAP`. Todas as 335 foram classificadas com evidencia HIGH como `CATALOG_ITEM_NOT_CREATED` no sentido preciso de **nenhum item criado/vinculado na colecao de destino**, embora registros editoriais existam e estejam vinculados a outra colecao. UNKNOWN = 0.

Causa raiz comprovada: `CatalogBuilderService.build()` calcula `collection_key` uma unica vez por pagina, percorrendo `page_refs`, para na primeira referencia cujo quarto segmento corresponde a uma colecao conhecida e aplica essa mesma colecao a todos os registros editoriais da pagina. Paginas historicas misturam varias pastas de inclusao; por isso registros posteriores sao associados ao primeiro agrupamento reconhecido, deixando as demais colecoes vazias.

Fluxo observado: HTML → Inventory OK → Parser OK → Catalog associa item a outra colecao → Normalization preserva → View agrega zero na colecao correta → API retorna HTTP 200/total 0.

Achado independente: `catalog_item_images` possui atualmente zero linhas em todos os builds persistidos, embora o run 10 registre 16.245 relacoes e o View 15 preserve 16.417 midias. O Image Parser run 2 terminou depois do Catalog run 10. Esta deriva temporal nao cria os 335 `items_count=0`, mas exige sequenciamento/rebuild controlado em ET futura.

## 6. Rastreamento historico → Inventory → Parser → Catalog → Normalization → View Model → API

- Acervo: 3593 imagens fisicas nas 335 pastas; 3359 referencias HTML resolvidas em 322 paginas.
- Inventory: 335/335 paths presentes; imagens categorizadas como `images`, legiveis; paginas HTML possuem item de Inventory.
- Parser: 335/335 reconhecidas por referencia; todas as 3359 referencias com status `resolved`; contextos: matched=3306, ambiguous=43, no_description=10.
- Catalog: 335/335 colecoes existem, mas com zero item; os registros editoriais correspondentes existem sob outra `collection_id`. A regra page-scoped/first-reference explica deterministicamente todos os casos.
- Normalization: 335 colecoes persistem, zero item com seu stable key; nao ha evento de merge/loss que explique o gap.
- View Model: 335 colecoes ready, `items_count=0`, `images_count=0`; consistente com a entrada normalizada.
- API: 335/335 detalhes HTTP 200, `collection.itemsCount=0`, `items.total=0`. Nenhuma perda adicional entre View e API nesses 335.

## 7. Padroes encontrados

- Todas as 322 paginas relevantes referenciam pelo menos duas pastas de colecao reconheciveis; o Catalog usa somente a primeira para todos os registros da pagina.
- 3.306 referencias possuem contexto `matched`; 43 `ambiguous`; 10 `no_description`. Logo, estrutura editorial imperfeita existe, mas nao explica a ausencia universal.
- Filenames resolvidos incluem extensao em caixa alta (1840 ocorrencias), espacos (266) e caracteres nao ASCII (4); como todos foram resolvidos, esses fatores nao sao causa raiz.
- Tabelas HTML e grupos HX001 predominam; grupos mistos exigem tratamento especial para nao dividir registros por heuristica de filename.

## 10. Caso fot-gio

Classificacao separada: `FOT_GIO_CROSS_TEAM_CATALOG_ASSOCIATION`, nao `API_EXPOSURE_GAP`. A colecao Catalog Torino/fot_gio tem 11 itens por `collection_id`, mas esses itens carregam `team_id`/team stable key de Roma, pois paginas de Roma referenciam a pasta Torino e a mesma regra de primeira referencia cruzou fronteiras de equipe. Normalization preserva a inconsistencia. O View agrega 11 itens/33 imagens na colecao Torino, mas materializa os 11 itens em rotas Roma/fot-gio. A API filtra corretamente `italia + torino + fot-gio` e retorna zero. A divergencia nasce antes da API, no Catalog, e se torna inconsistencia interna do View.

## 11. Causas raiz comprovadas

1. **Causa primaria dos 335:** binding de colecao por pagina e primeira referencia, em `catalog_builder_service.py`; deveria ser determinado por registro editorial/grupo estrutural.
2. **fot-gio:** a mesma regra aceita collection key de outra equipe sem validar compatibilidade com `tk`, criando item com team Roma e collection Torino.
3. **Deriva de midia separada:** Image Parser run posterior deixou `catalog_item_images` atual vazio enquanto runs/View mantiveram contagens historicas. Nao e causa de `items_count=0`, mas impede confiar no Catalog atual para relacoes de midia.

## 12. Casos UNKNOWN

Nenhum. A cadeia causal foi comprovada para 335/335 por dados persistidos e leitura da regra executada.

## 13. Correcoes minimas recomendadas para ET futura

- Catalog: calcular/validar `collection_key` por `EditorialRecord`, usando somente referencias do proprio registro; exigir que a colecao pertença ao mesmo team key da pagina.
- Grupos mistos: marcar review/split estrutural; nunca escolher por filename, quantidade ou ordem global da pagina.
- Pipeline: garantir ordem HTML Parser → Image Parser → Catalog → Normalization → View → Media e validar contagens reais antes de publicar run.
- fot-gio: fixture cruzada Roma/Torino e invariante `item.team_id == collection.team_id`.
- Somente depois das correcoes, rebuild integral controlado e comparacao de rotas/stable keys. Nada disso foi implementado nesta ET.
